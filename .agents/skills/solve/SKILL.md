# 계획 승인 기반 문제 풀이

## 1. 문제 이해와 계획만 작성

- 원문, 기존 코드, 실행 환경, 허용 도구·반입 규정을 읽기 전용으로 확인한다. 미확인은 구분한다.
- 키트의 templates/PLAN.md를 참고하여 문제 작업 폴더의 PLAN.md를 작성한다. 양식 원본과 기존 문서를 보존한다.
- 이 문제가 무엇을 주고 무엇을 구하는 문제인지 쉬운 설명과 예시로 풀어쓴다. 핵심 난점과 성공의 의미를 명시한다.
- 접근법·baseline·대안·선택 근거와 모듈 구조·데이터 흐름·파일 역할을 제안한다.
- 진행할 실험의 가설·변경 변수·고정 조건·평가·예상 비용을 작성한다.
- 작업을 B01, B02 등 블록으로 나누고 각 작업·입출력·테스트·예상 결과·완료 조건·시간을 정한다.
- 추가할 최소 하네스(실행·평가·로그·오류복구 등)와 문제별 정상·오류·경계·전체 흐름 검증을 제안한다. 필요성과 추가 비용도 적는다.
- 구현·설치·실험·테스트와 계획 외 파일 변경은 하지 않는다. PLAN을 보여주고 사용자 검토를 기다린다.

## 2. 수정 반영과 명시적 승인

- 사용자 수정사항을 PLAN에 반영하고 변경점을 설명한다. 수정 요청만으로 실행을 시작하지 않는다.
- 계획 버전과 승인된 블록 범위를 기록한다. 기본은 다음 블록 하나에 대한 승인이다.
- 사용자가 명시적으로 허락한 뒤에만 다음 단계로 넘어간다. 여러 블록을 한 번에 승인한 경우에만 그 범위까지 진행한다.
- 새 세션에서도 실제 승인 대화와 HANDOFF를 대조한다. 문서에 임의로 승인 상태를 만들어 쓰지 않는다.

## 3. 승인된 블록 실행

1. 실제 문제 저장소를 확인하고 승인 계획을 로컬 plan 커밋으로 남긴다. Git 사용은 AGENTS.md의 보존·stage 원칙을 따른다.
2. 블록 시작 전에 templates/EXPERIMENTS.md 형식으로 목표·작업·입출력·변경 파일·테스트·예상 결과를 기록하고 사용자에게 작업 범위를 알린다.
3. 승인 범위에서 최소 구현·실험을 수행한다. scripts/run_experiment.py 또는 기존 도구로 실행·seed·시간·종료·로그를 보존한다. 키트의 실제 경로를 사용한다.
4. 계획된 정상·오류·경계 테스트를 실행하고 실제 결과와 예상 결과를 비교한다. 테스트 실패 시 같은 블록 범위에서 수정·재검증하되 예산과 중단 조건을 지킨다.
5. EXPERIMENTS에 명령, 코드 버전·dirty 여부, run 경로, 결과, 실패, 한계, 사용자/AI 판단을 기록한다. 미실행·차단은 통과로 표시하지 않는다.
6. HANDOFF에 현재 상태와 다음 작업을 기록하고 해당 블록 변경·검증·문서를 하나의 의미 있는 로컬 block 커밋으로 남긴다. 완료 hash는 사용자에게 보고한다.
7. 작업·테스트 결과·Git commit·미해결 사항·다음 제안을 보고하고 멈춘다. 남은 승인 범위가 없으면 다음 블록의 허락을 기다린다.

## 4. 변경과 제출

- 목표·구조·데이터·평가·예산 변경은 PLAN 수정과 재승인을 거친다. 시간이 부족해져도 승인 절차를 생략하지 말고 범위 축소를 제안한다.
- 마지막 20%는 전체 흐름·재현성·제출 형식 검증에 사용한다. 블록 검증만으로 전체 동작을 확인했다고 주장하지 않는다.
- templates/SUBMISSION.md를 실제 명세로 채운다. 문제별 검사기는 승인된 계획에 따라 구현한다.
- 최종 보고는 실제 결과에 근거해 핵심 동작, 검증 방법, 직접 판단한 이유, 한계를 설명한다.
